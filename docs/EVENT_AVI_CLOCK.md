# AVI 内时间与纯 MP4 转码 — 2026-10-09

后续修正：设备时区已改为德国冬夏令时，联网 NTP 校时继续保留，详见
[CLOCK_SYNC.md](CLOCK_SYNC.md)。以下 GMT0 和固件摘要描述本次原始验收镜像。

用户确认：AVI 本身在右上角显示事件实际日期和时间；MP4 仅进行 H.264/AAC
转码，不再叠字。一轮监测仍只生成一个视频，删除静止间隔。

## 实现

事件 writer 在写入每帧前，将传感器 JPEG 解码成 full-range UYVY，绘制
白字黑底时间，再编码为 MJPEG。时间沿用设备时区；当前设备为 GMT0，本次
没有修改时区。候选静止尾帧保留采集时刻，只有恢复运动后实际写入的帧才处理。
Version-2 APP15 标记保留原采集时间供验收检查，显示不依赖播放器识别此标记。
采集时刻在帧处理入口记录，避免恢复运动时批量处理尾帧导致时间前移。
监测临时请求 15 FPS，保存带时间的事件画面临时请求 5 FPS；短暂静止候选帧
沿用相同节奏。结束事件后恢复监测节奏，停止监测后恢复用户原有录像参数。

JPEG 全帧缓冲和句柄仅在监测期间保留，停止后释放，避免阻止 idle VGA 编码。
固定版本 JPEG 组件的私有工作内存分配到 PSRAM，为相机、PDM 和 TCP 保留
内部 RAM。构建只适配该组件的两项分配调用，系统全局分配策略和 SDK 原文件保留。
MP4 转换器恢复为普通 JPEG 解码和 H.264 编码路径，不识别标记或绘制时间。
此前 idle 编码器初始化失败的 AVI 索引释放修复继续保留。

## 时长边界

- 没有固定五分钟或其他按分钟计的最长时长；通常由用户停止监测。
- 仅运动片段占播放时长；整轮监测期间没有已完成的第二个文件。
- AVI 1.0 的约 4 GiB 文件边界、4,294,967 帧、32-bit 累计有效时长边界，
  SD 最小剩余空间或写入/音频错误会结束录制。到边界停止，不另开第二个视频。
- 含 PCM 音频的文件通常先触及大小边界；实际时长随画面、压缩后帧大小
  和实测帧率变化，不能仅按帧数上限推算最长录制时间。
  当前网页下载通道独立限制在 2 GiB 减一字节；超过此大小的下载能力未建立。

## AVI 叠字引入的响应问题

初版同时保留 JPEG 内部工作区，监测准备完成后内部 RAM 仅余 14,240 字节；
顺序打开句柄仍曾降至 6,680 字节。较大的设置/状态响应在运动录制中超时。
SDK 的 JPEG 分配调用适配到 PSRAM 后，实测最低内部 RAM 提高到 26,260 字节。

单独修正内存后，持续 JPEG 工作仍让请求延迟 3.522 / 8.152 秒，状态请求超时。
帧处理超过 15 FPS 定时器间隔时，采集通知队列持续非空；原优先级高于 HTTP
和 PDM。因此监测期间将采集优先级降到 HTTP 之下，其他录制恢复原优先级。
组合修复后，运动录制中的设置、转码开关、状态响应分别为 0.110 / 0.095 /
0.047 秒。最终版本完整回归的监测状态响应最大 0.262 秒，停止请求最大
0.105 秒；这是本次短测试的观测值。

## 验证范围

新 AVI 的可见时间、完整 MJPEG/PCM 解码已经在真实板上确认。
录制时软件处理 JPEG 会降低实际帧率；事件录像目标 5 FPS 不代表始终达到 5 FPS。

最终版本的 **74 项真实板回归通过**。包括：VGA 上限与独立照片设置、

短暂静止恢复仍属同一事件、空监测无文件，以及先手动录像再连续两次 idle
转码。两次完整 MJPEG/PCM 和 H.264/AAC 解码通过，帧数及播放时长保留。
